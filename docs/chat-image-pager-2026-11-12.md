# 对话多图浏览修复

## 问题与改动

对话中的消息图片和图片记录打开详情时只传入了单个图片 ID。详情原来总从画廊的 `GalleryOrderSnapshot` 读取顺序：首次从对话打开通常退化为单张，若曾打开画廊图片又可能混入不相关的图库顺序。

现在消息入口传入本条消息的图片顺序，顶部图片记录入口传入该列表的顺序。快照在点击时去重并跳过已经没有本地文件的图片，单独保存到详情的导航条目，优先用于分页；从第二或第三张打开保持点击位置，不跳到首张。查看期间新完成的图片不改变这次快照，重新打开后可浏览新增结果。画廊入口继续使用原来的筛选顺序。

复用既有详情分页、收藏/保存操作与图片返回动效；没有更改生成请求、工具权限、费用、SFW、数据库或用户图片文件。此修复针对点开对话图片后的详情页；全屏缩放浮层仍保留既有缩放、拖动及关闭交互。

## 验证与交付

在现有云端 Android 实例构建和检查，实际多图操作使用独立、无网络权限的测试应用与本地色块图片，不发送真实聊天或生成请求。扩展既有聊天界面回归，核对从中间图片打开、左右切图、跳过缺失文件及返回后的列表位置；测试方法总数仍为 50。

最终代码 `4fff1f39d837478906d8724b4dde95b55c05909f` 的结果：

- 29 项 JVM 全部通过；聊天界面回归 1 项及其余设备回归 20 项全部通过，没有忽略或新增测试方法。第一次运行因测试暂停动画时钟，定位超长消息中的子图片无法等到滚动帧而中止；只在定位期间恢复测试时钟后，重新完成全部检查。
- Debug、设备测试包及 R8 优化包均构建成功。候选 `0.1.38 / code 38` 沿用云端测试证书覆盖安装，设备 APK 摘要匹配；无签名包与测试签名包的全部非签名内容一致，分享入口的 manifest 合同通过。
- 实际界面先打开画廊图片，留下旧图库顺序，再进入两组对话图片。第二组从最后一张打开并双向滑动，只在本组两张间切换；第一组从中间张打开，在三张图片之间正确切换，首尾停住，不进入另一组或缺失文件。
- 顶部图片记录按自身顺序 `4 → 5 → 0 → 1 → 2` 浏览，跨消息连续切换并跳过缺失文件；从非首张打开也保持点击位置。消息详情和图片记录返回后，对话图片边界、回看位置及输入区保持一致。
- 实际界面使用独立 `gallerybench` 优化包，已核对没有 INTERNET 权限。没有真实 LLM 或生图请求；云端软件渲染结果用于交互验收，不代表实体手机帧率。
